# Выгрузка Вордстата через API

Скрипт заменяет ручной сбор брендового спроса для отчёта об эффективности
наружной рекламы «Овсянникова». Было — около 80 открытий веб-интерфейса перед
каждым отчётом. Стало — одна команда: 192 вызова API, 3,84 ₽, сырые ответы на
диске, два файла на выходе. Прогон 09.09.2026 подтвердил схему на боевых
доступах — итоги в разделе «Первый боевой прогон».

```
config.yaml       периметр: фразы, даты, период, устройства
regions.yaml      справочник: наше название -> ID Вордстата -> кампания/контроль
run.py            единственная точка входа
ws/               код: api, periods, fetch, build, reconcile, regions
raw/YYYY-MM-DD/   сырые ответы, по файлу на вызов
output/YYYY-MM-DD/ wordstat_long.csv, wordstat_wide.xlsx, таблица сверки
tests/            57 тестов, сеть не нужна
```

## Быстрый старт

```bash
pip install -r requirements.txt
cp .env.example .env          # вписать ключ и folderId
python3 run.py plan           # что будет выгружено и почём — без обращений к API

python3 run.py regions fetch-tree   # разово: справочник регионов
python3 run.py regions resolve      # разово: проставить region_id
python3 run.py probe-regions        # разово: проверить, суммирует ли API регионы

python3 run.py fetch          # выгрузка по неделям (кэш, ретраи, лог стоимости)
python3 run.py build          # wordstat_long.csv + wordstat_wide.xlsx
python3 run.py reconcile --manual ручная_выгрузка.csv
```

Дневной срез и топ слов — теми же командами:

```bash
python3 run.py fetch --period PERIOD_DAILY    # по дням, глубина ~60 суток
python3 run.py build --period PERIOD_DAILY
python3 run.py top-export                     # что именно ищут: GetTop по всем парам
python3 run.py top-export --only "овсянников мыло" --limit 200 --tag core
```

**Прогон не укладывается в один час.** Квота сервиса — 100 запросов в час
(см. «Подводные камни API»), поэтому полный цикл из четырёх выгрузок идёт
около шести часов, окнами. Команды перезапускаемые: упёрлись в 429 — дождитесь
начала следующего часа и повторите ту же команду, уже полученное возьмётся из
кэша.

`fetch` перезапускаемый: уже полученные ответы берутся из кэша, после обрыва
достаточно повторить команду. Тесты — `python3 -m unittest discover -s tests -t .`

## Доступы: что сделать, по шагам

Квикстарт «Как начать работать с Yandex Search API» на сайте Яндекса подходит
целиком до пункта «Выполните первый поисковый запрос»: там показан веб-поиск
(`/v2/web/search`), а нам нужен Вордстат в том же сервисе. Настройка общая,
проверочный запрос — другой.

1. **Войти в [AI Studio](https://aistudio.yandex.cloud/platform/)** под Яндекс ID,
   создать организацию и облако. Каталог `default` создастся сам.
2. **Привязать платёжный аккаунт** — кнопка в правом верхнем углу. Статус должен
   стать `ACTIVE` или `TRIAL_ACTIVE`. Без активного платёжного аккаунта вызовы
   отвечают `Permission denied`, даже когда ключ и роль верные.
3. **Создать API-ключ** — кнопка «Создать API-ключ». Вместе с ним заводится
   сервисный аккаунт с ролью для Search API. Секретное значение показывается
   один раз, скопировать сразу.
4. **Взять `folderId`** — идентификатор каталога, в котором создан ключ:
   консоль Yandex Cloud, раздел каталога, строка вида `b1g…`.
5. **Проверить роль.** Сервисному аккаунту нужна `search-api.webSearch.user`.
   Консоль → каталог → Права доступа. Если её нет — выдать.
6. **Заполнить `.env`** в каталоге `wordstat/`:

   ```
   YANDEX_API_KEY=AQVN…
   YANDEX_FOLDER_ID=b1g…
   ```

7. **Проверить связь** — запрос к Вордстату, а не к веб-поиску:

   ```bash
   set -a; source .env; set +a
   curl -sS -X POST 'https://searchapi.api.cloud.yandex.net/v2/wordstat/dynamics' \
     -H "Authorization: Api-Key $YANDEX_API_KEY" \
     -H 'Content-Type: application/json' \
     -d '{"phrase":"овсянников мыло","period":"PERIOD_WEEKLY",
          "fromDate":"2026-08-03T00:00:00Z","toDate":"2026-09-06T23:59:59Z",
          "folderId":"'"$YANDEX_FOLDER_ID"'"}'
   ```

   Ответ вида `{"results":[{"date":"…","count":"…","share":…}]}` означает, что
   доступ есть. `Permission denied` — смотреть шаги 2 и 5; `INVALID_ARGUMENT` —
   `folderId` или формат дат.

Дальше всё делает скрипт. Ключей в репозитории нет и быть не должно: `.env`
в `.gitignore`, скрипт читает переменные окружения и без них останавливается
с понятным сообщением.

### Запуск в облачной сессии Claude Code

Домен `searchapi.api.cloud.yandex.net` не входит в список Trusted, поэтому в
окружении сессии его нужно разрешить: claude.ai/code → значок окружения над
полем ввода → шестерёнка → **Network access: Custom** → в **Allowed domains**
добавить домен и отметить **Also include default list of common package
managers** (иначе не поставится openpyxl).

Ключ и каталог можно передать двумя способами:

- **Environment variables** окружения — обычные `YANDEX_API_KEY` и
  `YANDEX_FOLDER_ID`. Просто, но значение видно всем, кто пользуется
  окружением, и доступно самой сессии.
- **API credentials** окружения (планы Pro и Max) — надёжнее: ключ хранится
  вне песочницы, прокси подставляет заголовок уже после того, как запрос
  вышел из сессии, и в переменные окружения ключ не попадает. Тип **Bearer**,
  **Allowed websites** — `searchapi.api.cloud.yandex.net`, **Custom headers**:
  имя `Authorization`, префикс `Api-Key`, значение — сам ключ. В этом случае
  вместо `YANDEX_API_KEY` задайте `YANDEX_AUTH_VIA_PROXY=1`, и скрипт не будет
  ставить заголовок сам. Хост из API-доступов открывается для сети независимо
  от уровня Network access.

Настройки окружения читаются один раз при старте сессии: после правки нужна
**новая** сессия, уже запущенная работает со старой политикой.

## Запуск на своём компьютере

Нужен Python 3.9 или новее. Проверить: `python3 --version` (в Windows —
`py --version`; дальше вместо `python3` пишите `py`).

```bash
git clone -b claude/new-session-w46wfu https://github.com/vsalenko2026/ovsyannikov-ooh-analytics.git
cd ovsyannikov-ooh-analytics/wordstat
python3 -m pip install -r requirements.txt
```

Создайте в каталоге `wordstat` файл `.env` — обычным блокнотом, две строки:

```
YANDEX_API_KEY=AQVN…
YANDEX_FOLDER_ID=b1g…
```

Дальше по порядку:

```bash
python3 run.py regions fetch-tree     # справочник регионов, бесплатно
python3 run.py regions resolve        # проставить ID; посмотреть, все ли нашлись
python3 run.py plan                   # 192 вызова, 3,84 ₽ — сверить перед тратой
python3 run.py probe-regions          # разовая проверка поведения API

python3 run.py fetch                  # недельный ряд
python3 run.py build
python3 run.py fetch --period PERIOD_DAILY    # дневной ряд
python3 run.py build --period PERIOD_DAILY
python3 run.py top-export             # топ вложенных запросов
python3 run.py top-export --only "овсянников мыло" --only "овсянников косметика" \
                          --only "овсянников купить" --limit 200 --tag core
```

Результат — четыре каталога в `output/`: `ГГГГ-ММ-ДД`, `…-day`, `…-top`,
`…-top-core`. Сырые ответы остаются в `raw/` и нужны для воспроизводимости —
не удалять.

Если что-то упало, прогон перезапускается той же командой: уже полученное
берётся из кэша, API повторно не дёргается.

**Заложите на всё около шести часов.** Квота — 100 запросов в час, весь цикл это
720 вызовов, то есть семь часовых окон. Упёрлись в 429 — это не поломка:
дождитесь начала следующего часа UTC и повторите ту же команду.

## Еженедельное расписание

Полный цикл идёт по средам, семью шагами, по одному на часовое окно квоты.
Каждый шаг — отдельная задача в Claude Code: поднимается новая сессия,
выполняет `bash tools/step.sh N`, коммитит `raw/` и `output/` и пушит.

| Шаг | Время МСК | UTC | Что делает | Вызовов |
|---|---|---|---|---|
| 1 | 12:00 | 09:00 | недельный ряд, группа фраз 1 | 96 |
| 2 | 13:00 | 10:00 | недельный ряд, группа 2, сборка | 96 |
| 3 | 14:00 | 11:00 | дневной ряд, группа 1 | 96 |
| 4 | 15:00 | 12:00 | дневной ряд, группа 2, сборка | 96 |
| 5 | 16:00 | 13:00 | топ слов, группа 1 | 96 |
| 6 | 17:00 | 14:00 | топ слов, группа 2, сборка | 96 |
| 7 | 18:00 | 15:00 | углублённый топ по ядру, глубина 200 | 72 |

Итого 648 вызовов за среду, около 13 ₽ по тарифу из ТЗ.

Группы фраз считаются, а не вписаны руками: `run.py chunks` делит периметр
так, чтобы каждая группа укладывалась в 100 вызовов в час. Добавили фразу —
разбивка пересчитается сама; если групп станет больше двух, `tools/step.sh`
остановится и скажет, что расписание нужно пересобрать под новое число шагов.

Среда выбрана не случайно: последняя закрытая неделя к этому моменту уже
закрыта, и в ряд попадает полный понедельник–воскресенье.

## Источник данных

Wordstat — сервис внутри Yandex Search API v2 (AI Studio). Веб-парсинг не
используется. Авторизация — заголовок `Authorization: Api-Key <ключ>`,
`folderId` обязателен в теле каждого запроса.

| Метод | Путь | Где используется |
|---|---|---|
| `GetDynamics` | `POST /v2/wordstat/dynamics` | основной сценарий, `run.py fetch` |
| `GetRegionsTree` | `POST /v2/wordstat/getRegionsTree` | `run.py regions fetch-tree`, не тарифицируется |
| `GetTop` | `POST /v2/wordstat/topRequests` | `run.py top` — разбор омонимов |

## Принятые решения

**Область, а не город.** `meta.level: oblast` в `regions.yaml`. Периметр кампании
задан городами, но контрольная группа изначально набрана областями, а сравнивать
город с областью нельзя: уровень должен быть одинаковым для обеих групп. Города
сохранены в поле `cities` — если заказчик решит иначе, меняется справочник, не код.

**Тюменская область — узел 11176, без округов.** Проверено 09.09.2026 по
`GetRegionsTree`: у неё ровно четыре дочерних узла — Ишим, Тобольск, Тюмень,
Ялуторовск. ХМАО-Югра (11193) и ЯНАО (11232) лежат в дереве не под ней, а
рядом, прямыми детьми узла «Урал», поэтому спрос округов в ряд не попадает.
Решение записано в `note` у региона в справочнике.

**Кемеровская область называется «Кемеровская область (Кузбасс)».** В круглых
скобках, а не через тире. С первого прохода `regions resolve` узел не нашёлся;
точное написание добавлено в `match`, регион разрешается в 11282. Если сервис
переименует ещё какой-то субъект, лечится так же — правкой `match`, не кода.

**Один регион на вызов.** По документации `regions[]` — «список регионов, из
которых сделан запрос»: ответ приходит одним рядом, без разбивки. Проверяется
эмпирически командой `probe-regions`: она делает три вызова (регион A, регион B,
A+B) и сравнивает суммы. Если подтвердится суммирование — текущая схема верна;
если нет, сырые ответы останутся в `raw/probe/` для разбора. Разбивку по регионам
умеет отдельный метод `GetRegionsDistribution`, но он даёт срез, а не динамику.

**Границы недель не пересобираются.** Скрипт не строит недельную сетку сам. Он
берёт дату из ответа API и определяет, с какого края недели она проставлена
(`week_anchor: auto`): все даты понедельники — начало недели, все воскресенья —
конец. Смешанный набор — сборка останавливается с ошибкой, а не достраивает
границы наугад. Определённый якорь пишется в `build.json` и печатается в консоль.

**Незакрытая неделя.** По умолчанию не запрашивается: `toDate` выравнивается на
конец последней **закрытой** недели. Если включить `series.include_current_period`,
неполная неделя попадёт в выгрузку с `is_partial=1` в CSV и подсветкой в XLSX.
Молча в расчёт множителей она не попадает ни при каком режиме.

**Омонимы не фильтруются.** По Орловской области запрос со словом «купить»
собирает шум от названия региона. Скрипт выгружает как есть — фильтрация на
этапе анализа, чтобы сырые данные оставались сырыми. Разобрать структуру шума:
`python3 run.py top --phrase "овсянников купить" --region "Орловская область"`.

## Четыре вида выгрузки

| Команда | Что даёт | Глубина | Вызовов |
|---|---|---|---|
| `fetch` | недельный ряд частотности | с 2018 года | 192 |
| `fetch --period PERIOD_DAILY` | дневной ряд | последние ~60 дней | 192 |
| `top-export` | топ вложенных запросов и ассоциаций | срез за 30 дней | 192 |
| `top-export --only … --tag core` | углублённый топ по ядру метрики | срез за 30 дней | 72 |

8 фраз × 24 региона = 192 вызова, 3,84 ₽ за прогон. Углублённый топ берёт
только три фразы ядра, зато с `--limit 200` вместо 50: на боевых данных это
дало 62 вложенных запроса на фразу против 43 при лимите 50.

Каталоги не смешиваются: `raw/2026-09-09/` — недели, `raw/2026-09-09-day/` —
дни, `raw/2026-09-09-top/` — топ, `raw/2026-09-09-top-core/` — топ с меткой
`--tag core`. Сборка определяет период по сохранённым
запросам и отказывается собирать каталог, где периоды перемешаны.

**Дневная выгрузка не заменяет недельную.** Дневная детализация у Вордстата
живёт около 60 суток, то есть окна «до» старта кампании (17.07 и 04.06) в ней
уже нет. Множители difference-in-differences считаются по недельному ряду;
дневной нужен, чтобы увидеть форму отклика внутри кампании — на какой день
после старта пошёл спрос, как он затухает, что происходит в дни акций.
Скрипт сам сдвигает начало ряда до доступной глубины и печатает
предупреждение.

**Топ слов — срез, а не ряд.** `GetTop` отдаёт вложенные запросы за последние
30 дней без разбивки по датам, поэтому снимок помечается датой прогона. Два
применения: раздел «что именно ищут» в отчёте и разбор омонимов — по
Орловской области видно, какая доля запроса со словом «купить» приходится на
название региона, а не на бренд.

## Форматы выгрузки

**`output/YYYY-MM-DD/wordstat_long.csv`** — длинный формат, основной для анализа:

```
date, week_start, week_end, phrase, region_name, region_id, region_type, device, count, share, is_partial
```

`is_partial` — колонка сверх ТЗ: 1 означает, что неделя на момент выгрузки не
закрыта. Кодировка UTF-8 с BOM, разделитель — запятая.

**`output/YYYY-MM-DD/wordstat_wide.xlsx`** — широкий, для глазной проверки:
лист на фразу, строки — недели, колонки — регионы. Кампания идёт первой, по
убыванию числа экранов, затем контроль. Незакрытые недели подсвечены.

**`output/YYYY-MM-DD-top/wordstat_top.csv`** — топ вложенных запросов:

```
fetched_at, phrase, region_name, region_id, region_type, device, kind, rank, nested_phrase, count, total_count
```

`kind` — `nested` (вложенный запрос) или `association` («с этим ищут»).
Рядом `wordstat_top.xlsx`: лист на фразу, строки — вложенные запросы по
убыванию суммарной частоты, колонки — регионы; ассоциации отдельными листами.

В дневной выгрузке колонки `week_start` и `week_end` равны самой дате — формат
файла один для всех периодов.

Каталог результата назван датой прогона и не перезаписывается: повторная сборка
поверх требует `--force`.

## Сверка с ручной выгрузкой

Обязательный этап приёмки. Пока не пройден — скрипт не считается готовым.

```bash
python3 run.py reconcile --manual ручная_выгрузка.csv
```

Ручная выгрузка — таблица (csv, tsv или xlsx) с четырьмя колонками; заголовки
распознаются по названию, порядок неважен:

| фраза | регион | дата | частота |
|---|---|---|---|
| овсянников мыло | Ярославская область | 2026-07-13 | 41 |

В колонке «регион» можно писать город («Ярославль») — сопоставится через
`cities` из справочника. Дата — любой день недели, приводится к её началу.

На выходе — `сверка_с_ручной_выгрузкой.md` и `.csv`: неделя, значение ручное,
значение из API, расхождение в процентах. Пороги:

| Условие | Итог |
|---|---|
| расхождение до 2% на отдельных неделях | приемлемо, фиксируется здесь, в README |
| медиана расхождений > 1% | СТОП |
| отдельное расхождение > 10% | СТОП |
| суммарное отношение API/ручная вне [0,98; 1,02] | СТОП |
| строка ручной выгрузки не нашла пары | СТОП |

Коэффициентами не подгонять. Разбираться в таком порядке: операторы в фразе,
трактовка словоформ, ID региона в справочнике, границы недель.

### Признанные расхождения с веб-интерфейсом

Раздел заполняется по результату первой сверки — пока доступов нет, он пуст.

## Периметр

24 региона: 17 кампании (19 городов, свёрнуты в субъекты федерации) и 7
контрольных. Источник — фактический список размещения на 17.07.2026. Ярославская
область идёт отдельной строкой: `campaign_start: 2026-06-04`, у остальных
`2026-07-17`.

Восемь фраз. Первые три — ядро метрики (`овсянников мыло`, `овсянников
косметика`, `овсянников купить`), на них построены все ранее опубликованные
множители. Остальные пять (`овсянников крем`, `овсянников сайт`, `овсянников
тайный советник`, `ovsyannikovsoap`, `ovsyannikov`) согласованы дополнительно
и выгружаются наравне; какие из них идут в расчёт множителей, решается на
этапе анализа. `овсянников отзывы` не берём — однофамилец, чистый эффект ×0,23.

`овсянников образцы` была снята после первого прогона: 24 региона из 24
ответили, ряд полной длины 23 недели, частота везде ноль. Множитель на нуле не
считается, поэтому фраза убрана из `config.yaml`. Сырые ответы по ней остались
в `raw/2026-09-09/` — сборка отбирает записи по периметру из конфига и в CSV
их не пускает.

Прогон: 8 фраз × 24 региона × 1 срез устройств = 192 вызова, 3,84 ₽.

## Первый боевой прогон, 09.09.2026

Схема подтверждена на живых доступах. Выгружено 672 ответа, 13,44 ₽ по тарифу
из ТЗ. Заняло 5 ч 41 мин (17:20 → 23:01 UTC), из них полезной работы около семи
минут — остальное ожидание часовой квоты, семь окон подряд по 100 вызовов.

| Выгрузка | Ответов | Что получилось |
|---|---|---|
| недельная | 192 | 4416 строк = 8 фраз × 24 региона × 23 недели, 30.03 … 06.09 |
| дневная | 192 | 11136 строк = 8 × 24 × 58 дней, 12.07 … 07.09 |
| топ, 8 фраз | 192 | 1825 строк: 347 вложенных запросов, 1478 ассоциаций |
| топ, ядро (`--limit 200`) | 72 | 964 строки: 186 вложенных, 778 ассоциаций |

Полнота проверялась не суммой файлов, а каждой парой «фраза × регион» против
справочника, плюс равенством длины ряда у всех фраз. Пропусков нет, усечённых
рядов нет.

**Якорь недели — `start`.** Определён автоматически: все даты в ответах пришли
понедельниками, смешанного набора не было. Записан в `build.json`.

**Незакрытых недель нет.** `is_partial=1` не встретился ни в одной строке,
`partial_weeks: []` — ряд обрывается на последней закрытой неделе, как и задано
`include_current_period: false`.

**Дневной ряд обрезан глубиной сервиса.** Начало сдвинуто с 30.03 на 12.07,
осталось 58 дней. До старта основной программы (17.07) в нём пять дней, до
ярославского пилота (04.06) — ноль. Множители difference-in-differences
считаются только по недельному ряду.

**Пустой ответ — это не ошибка.** Курганская область по всем трём фразам ядра
вернула 0 вложенных и 0 ассоциаций, поэтому в `output/2026-09-09-top-core/`
регионов 23, а не 24, при 72 файлах из 72. Спроса там просто нет, и сборка не
создаёт пустых строк.

**Шум по «овсянников купить» шире, чем ожидалось.** Ассоциации по этой фразе:
`купля продажа` 213 150, `моя цена` 23 606, `я покупаю` 21 462, `отдел продаж`
15 721 — общеторговая лексика на три порядка выше брендовых вложенных запросов.
Ранее предполагалось, что шумит название Орловской области; на деле шумит само
слово «купить», во всех регионах. Раздел «что именно ищут» по этой фразе
разбирать по вложенным запросам, а не по ассоциациям, и отдельно проверить, не
завышена ли её недельная частота — она наибольшая из восьми.

## Подводные камни API

Проверено по документации сервиса и разборам; часть подтвердится только на
боевых доступах.

- `toDate` обязан быть последним днём периода, иначе `InvalidArgument: The to
  field value should be the last day of the week`. Выравнивание делает
  `ws.periods.period_end`.
- `period` — только с префиксом: `PERIOD_WEEKLY`, не `WEEKLY`.
- `count` приходит **строкой** (особенность proto для int64) — приводится к int
  в `ws.api.dynamics_rows`.
- **Нулевую неделю сервис отдаёт без `count` и без `share`**: точка приходит как
  `{"date": "2026-03-30T00:00:00Z"}`. Поля пропадают строго парой, случая
  «share без count» на боевых данных не встретилось ни разу. На прогоне
  09.09.2026 таких точек 67% (1520 из 2277). Пропуск читается как ноль в обоих
  местах разбора — `ws.api.dynamics_rows` и `ws.build.to_rows`.
- `manifest.json` в каталоге прогона описывает **последний запуск команды**, а
  не всю выгрузку: при перезапуске он перезаписывается. Считать стоимость по
  нему нельзя — после прогона окнами он покажет только последнее окно. Верный
  счёт — по числу сохранённых ответов в каталоге.
- Операторы в `GetDynamics` зависят от детализации: **по дням принимаются все**
  (`!`, кавычки, `[]`, `()`, `|`), по неделям и месяцам — только `+`. Скрипт
  проверяет фразу до вызова с учётом периода и не тратит квоту на заведомый
  отказ. Отсюда практический ход: точную частотность с операторами можно снять
  только дневной выгрузкой.
- `fromDate` при недельной агрегации должен быть понедельником, `toDate` —
  воскресеньем; при месячной — первым и последним днём месяца. Выравнивание
  делает скрипт.
- API-ключ должен иметь область действия `yc.search-api.execute`. Ключ,
  выпущенный без неё, отвечает отказом авторизации при верной роли.
- **Квота — 100 запросов в календарный час UTC**, а не «5–10 в секунду», как
  предполагалось до боевого прогона. Проверено 09.09.2026: отказ приходит с
  текстом `search-api.wordstatRequestsPerHour.rate rate quota limit exceed:
  allowed 100 requests`, а лимит отпускает ровно на границе часа — окно
  фиксированное, не скользящее. Заголовка `Retry-After` в отказе нет.
  `getRegionsTree` тоже расходует квоту, хотя не тарифицируется.
  Практика: полный цикл из четырёх выгрузок (720 вызовов) занимает семь окон,
  около шести часов. Пауза `api.pause_seconds` (0,3 с) к квоте отношения не
  имеет — она защищает от всплеска, но потолок задан часом.
- Упёршись в квоту, скрипт честно ретраит каждый вызов 5 раз с задержками
  2 / 4 / 8 / 16 с и тратит на заведомо обречённый вызов около 30 секунд.
  На остатке большого плана это часы холостой работы: дешевле дождаться начала
  следующего часа и повторить команду — кэш не даст выгрузить одно и то же
  дважды.
- Вызовы, упавшие с 5xx, 401, 403 и 429, не тарифицируются и в стоимость прогона
  не входят.
- Тариф в логе взят из ТЗ: 0,02 ₽ за вызов (`api.price_per_call_rub`). Есть
  сведения, что Wordstat в составе AI Studio сейчас бесплатен — проверить по
  первому счёту и, если так, поставить 0.

## Что осталось

- **Сверка с ручной выгрузкой.** Единственный незакрытый этап приёмки. Нужна
  таблица ручной выгрузки от заказчика; команда и пороги — в разделе «Сверка с
  ручной выгрузкой». Боевой прогон её не заменяет: он показывает, что данные
  выгружаются полно и непротиворечиво, но не что они совпадают с
  веб-интерфейсом.
- **Число экранов.** В досье 114 экранов основной программы плюс 7 в Ярославле,
  но таблица фактического размещения даёт в сумме 117 (110 без Ярославля).
  На выгрузку не влияет — `screens` в справочнике только для порядка колонок,
  но при сверке периметра расхождение стоит закрыть.
- **Запуск по расписанию** (Cloud Function + таймер + уведомление в телеграм) —
  отдельная задача второго шага, здесь сознательно не делается.
